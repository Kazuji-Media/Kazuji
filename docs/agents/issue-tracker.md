# Issue tracker

O tracker principal deste checkout é GitHub: https://github.com/Kazuji-Reader/Kazuji.
Repositórios de origem e relacionados só entram na spec após definição do escopo pelo mantenedor.

## Acesso

Preferir o conector GitHub disponível para ler issues, comentários, labels, responsáveis e pull requests e para registrar specs. O CLI gh é fallback quando conectividade e autenticação estiverem disponíveis. Nesta sessão a consulta CLI falhou por proxy indisponível; o conector funcionou.

## Convenções

- Preservar os labels atuais: type:task, area:mobile e area:docs foram observados na issue do inventário. Não criar vocabulário paralelo sem necessidade.
- Ler corpo e comentários antes de classificar; confirmar comportamento no código e por validação apropriada.
- Salvar rascunhos e evidências em docs/plans; publicar a spec como issue depois de consolidar o escopo. Vincular as issues originais.
- Reutilizar issues existentes. Usar sub-issues e dependências nativas quando disponíveis; fallback: lista de tarefas e links explícitos para bloqueadores.
- Atribuir a issue ao usuário autenticado antes da implementação, conforme AGENTS.md.
- Comentários de triagem começam com: *This was generated by AI during triage.*
- Registrar evidência de resolução antes de fechar. Correção exclusiva na fork não comprova resolução na origem.
- Para texto multilinha no CLI, usar arquivo e --body-file. Não embutir texto complexo em comandos shell.

## Pull requests

Consultar PRs relacionados para identificar trabalho já feito. Criar PR de integração quando houver alterações verificadas e anexá-lo ao chat. Não mesclar nem encerrar issues por inferência de um build bem-sucedido.
